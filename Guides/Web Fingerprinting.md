# Web Fingerprinting

## Overview

Web fingerprinting is the process of identifying the technologies and software components powering a website or web application. By analysing HTTP responses, server banners, page content, and application behaviour, security professionals can build a profile of the target's infrastructure.

Fingerprinting is an essential part of web reconnaissance because it helps identify technologies, detect potential misconfigurations, and determine which vulnerabilities should be investigated during subsequent security assessments.

Common fingerprinting targets include:

- Web servers, such as Apache, Nginx, and Microsoft IIS.
- Operating systems and server platforms.
- Content Management Systems (CMS), such as WordPress and Joomla.
- Programming languages and application frameworks.
- Web Application Firewalls (WAFs).
- Outdated software and potentially insecure configurations.

**Important:** Identifying a technology does not automatically mean that it is vulnerable. Fingerprinting provides information that helps guide further investigation.

## 1. Fingerprinting Techniques

### 1.1 Banner Grabbing

Banner grabbing involves collecting information exposed by a network service. Web servers may disclose their software name, version, and other implementation details through HTTP response headers.

Use `curl` with the `-I` option to retrieve HTTP response headers:

```bash
curl -I http://inlanefreight.com
```

Example response:

```http
HTTP/1.1 301 Moved Permanently
Date: Fri, 31 May 2024 12:07:44 GMT
Server: Apache/2.4.41 (Ubuntu)
Location: https://inlanefreight.com/
Content-Type: text/html; charset=iso-8859-1
```

The response reveals several details:

- `301 Moved Permanently`: The requested resource has been permanently redirected.
- `Server: Apache/2.4.41 (Ubuntu)`: The server identifies itself as Apache 2.4.41 running on Ubuntu.
- `Location`: Specifies the destination of the redirect.
- `Content-Type`: Indicates the media type of the response body.

Since the server redirects HTTP traffic to HTTPS, inspect the destination as well:

```bash
curl -I https://inlanefreight.com
```

Example response:

```http
HTTP/1.1 301 Moved Permanently
Server: Apache/2.4.41 (Ubuntu)
X-Redirect-By: WordPress
Location: https://www.inlanefreight.com/
Content-Type: text/html; charset=UTF-8
```

The `X-Redirect-By: WordPress` header suggests that WordPress initiated the redirect.

Follow the redirect chain to inspect the final destination:

```bash
curl -I https://www.inlanefreight.com
```

Example response:

```http
HTTP/1.1 200 OK
Server: Apache/2.4.41 (Ubuntu)
Link: <https://www.inlanefreight.com/index.php/wp-json/>; rel="https://api.w.org/"
Content-Type: text/html; charset=UTF-8
```

The `wp-json` path and `api.w.org` relation provide additional evidence of a WordPress installation and its REST API.

**Note:** Server banners and application-specific headers can be modified, suppressed, or generated by intermediary systems. They should be treated as clues rather than definitive proof of the underlying infrastructure.

### 1.2 Analysing HTTP Headers

HTTP headers can reveal information about the server, application, and security configuration.

Useful headers include:

| Header | Potential Information |
|---|---|
| `Server` | Web server software and version. |
| `X-Powered-By` | Programming language or application technology. |
| `Set-Cookie` | Session mechanisms and application-related identifiers. |
| `Location` | Redirect destinations. |
| `Link` | Related resources, APIs, and metadata. |
| `X-Redirect-By` | Component that reports initiating a redirect. |
| `Strict-Transport-Security` | Browser policy for subsequent HTTPS connections. |
| `X-Content-Type-Options` | Browser content-type handling policy. |

To display response headers without downloading the response body:

```bash
curl -sD - -o /dev/null https://www.inlanefreight.com
```
